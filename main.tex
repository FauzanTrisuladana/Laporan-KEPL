\section{Hasil dan Pembahasan}

\par Laporan Ujian Tengah Semester (UTS) ini memuat dokumentasi komprehensif atas seluruh hasil perancangan, implementasi fitur, otomasi pengujian, dan evolusi perangkat lunak yang telah diselesaikan secara berkesinambungan dari Tugas 1 hingga Tugas 5 pada mata kuliah Konstruksi dan Evolusi Perangkat Lunak. Pembahasan disusun secara kronologis dan terstruktur, merefleksikan setiap penambahan kapabilitas sistem mulai dari inisialisasi repositori Git dan integrasi awal \textit{Continuous Integration} (CI), penerapan \textit{Continuous Delivery} (CD) multi-tahap dan skrip \texttt{deploy.sh}, penyediaan REST API dan perancangan antarmuka \textit{Single Page Application} (SPA) Vue 3, kontainerisasi aplikasi berbasis FrankenPHP dan optimasi \textit{layer caching}, hingga refaktorisasi citra \textit{multi-stage build} minimalis Alpine Linux dengan pengerasan keamanan pengguna \textit{non-root}, pemantauan kesehatan via \texttt{HEALTHCHECK}, serta penerbitan otomatis citra ke GitHub Container Registry (GHCR).

\subsection{Tugas 1: Pengembangan Aplikasi Web Sederhana (Laravel)}

\par Repositori ini memuat aplikasi web fungsional yang dibangun di atas \textit{framework} Laravel 11 dengan bahasa pemrograman PHP versi 8.4. Aplikasi yang dikembangkan dirancang sebagai modul URL Shortener sederhana yang dilengkapi dengan sistem autentikasi pengguna (\textit{login} dan \textit{register}), manajemen pembuatan dan pengalihan tautan singkat (\textit{links}), serta pencatatan analitik pengunjung (\textit{visitors}).

\par Pada aspek arsitektur perangkat lunak, sistem mengimplementasikan pola desain \textit{Model-View-Controller} (MVC). Struktur basis data dikelola melalui skema migrasi tabel (\textit{database migrations}) yang terhubung dengan model Eloquent: \texttt{User} untuk menyimpan kredensial pengguna, \texttt{Link} untuk menyimpan relasi URL asli dengan kode tautan pendek, serta \texttt{Visitor} untuk mencatat metadata alamat IP, \textit{user agent}, dan waktu akses pengunjung. Seluruh logika autentikasi dikendalikan oleh \texttt{AuthController} yang terintegrasi dengan berkas \textit{routing} \texttt{routes/web.php} serta tampilan antarmuka Blade modern yang responsif dengan dukungan tema gelap (\textit{dark theme}).

\subsection{Tugas 1: Penerapan Mutu Pesan Commit (Conventional Commits)}

\par Dalam disiplin rekayasa perangkat lunak modern, kejelasan catatan \textit{commit history} merupakan cerminan profesionalisme dan keteraturan pengembang. Berdasarkan kriteria penugasan praktikum, penulisan pesan commit wajib mematuhi spesifikasi standar \textit{Conventional Commits} dengan format baku:
\begin{center}
    \texttt{<type>(<scope>): <subject>}
\end{center}
Pesan commit yang tidak bermakna seperti "update", "fix bug", atau deskripsi ambigu lainnya dihindari sepenuhnya. Penerapan konvensi ini memberikan manfaat penting dalam mempermudah \textit{code review}, melacak riwayat perubahan secara kronologis, memfasilitasi pelacakan regresi kode (\textit{git bisect}), serta memungkinkan pembuatan catatan rilis (\textit{changelog}) secara otomatis.

\par Pada repositori ini, seluruh commit telah mengimplementasikan konvensi semantik tersebut secara konsisten. Rincian riwayat commit yang tercatat di dalam repositori diuraikan sebagai berikut:
\begin{itemize}
    \item \texttt{4059021 - feat(project)}: Inisialisasi awal struktur repositori proyek, pengaturan lisensi sumber terbuka, dan pembuatan dokumentasi awal pada berkas \texttt{README.md}.
    \item \texttt{037c383 - feat(project)}: Instalasi \textit{framework} Laravel 11 beserta dependensi pustaka inti PHP versi 8.4 ke dalam direktori kerja proyek.
    \item \texttt{f6042bf - feat(workflow)}: Pembuatan dan penambahan berkas konfigurasi otomasi CI (\texttt{.github/workflows/ci.yml}) untuk pengujian unit dan linting kode otomatis.
    \item \texttt{24fa6c1 - fix(ci state)}: Penyesuaian aturan pemicu (\textit{triggers}) pada berkas CI agar merespons aktivitas \textit{push} dan \textit{pull request} pada \textit{branch} \texttt{main}, \texttt{dev}, serta \textit{feature branch} (\texttt{feature/**}).
    \item \texttt{d455005 - feat(migration, model)}: Penambahan skema migrasi basis data untuk tabel \texttt{users}, \texttt{links}, dan \texttt{visitors}, pendefinisian relasi model Eloquent, serta penyesuaian dependensi workflow CI.

\end{itemize}
\par Riwayat commit di atas membuktikan bahwa setiap commit mewakili satu unit perubahan fungsional yang teratomisasi (\textit{atomic commit}), sehingga evolusi kode sumber terdokumentasi secara transparan dan teratur.

\subsection{Tugas 1: Manajemen Branching Workflow dan Pull Request}

\par Strategi manajemen \textit{branching} yang diterapkan pada repositori ini mengadopsi variasi standar industri \textit{Git Flow} dengan struktur tiga tingkatan hierarki \textit{branch}:
\begin{enumerate}[label=\arabic*.]
    \item \textbf{\textit{Main Branch} (\texttt{main})}: Berfungsi sebagai \textit{branch} rilis utama yang hanya memuat kode yang telah teruji secara penuh, stabil, dan siap dijalankan di lingkungan produksi. Segala bentuk \textit{direct push} ke \textit{branch} ini dilarang keras melalui aturan \textit{branch protection}.
    \item \textbf{\textit{Development Branch} (\texttt{dev})}: Berfungsi sebagai \textit{branch} integrasi aktif tempat fitur-fitur baru digabungkan dan diuji secara komparatif sebelum dinyatakan siap dirilis ke \textit{branch} \texttt{main}.
    \item \textbf{\textit{Feature Branch} (\texttt{feature/ci})}: Dibuat sebagai turunan dari \textit{branch} \texttt{dev} untuk mengerjakan fitur otomasi CI secara terisolasi tanpa mengganggu stabilitas basis kode yang sedang aktif dikembangkan.
\end{enumerate}

\par Sesuai dengan batasan instruksi tugas, penggabungan kode dari \textit{feature branch} hingga mencapai \textit{main branch} wajib melalui dua tahapan \textit{Pull Request} (PR):
\begin{itemize}
    \item \textbf{Pull Request \#1 (\texttt{feature/ci} $\rightarrow$ \texttt{dev})}: Bertujuan meninjau dan mengintegrasikan konfigurasi \textit{workflow} CI awal dari \textit{feature branch} ke dalam \textit{branch} pengembangan \texttt{dev}.
    \item \textbf{Pull Request \#2 (\texttt{dev} $\rightarrow$ \texttt{main})}: Bertujuan menggabungkan seluruh hasil pengembangan aplikasi yang telah stabil dari \textit{branch} \texttt{dev} menuju \textit{branch} produksi \texttt{main} sebagai rilis awal tugas.
\end{itemize}

\subsection{Tugas 1: Konfigurasi Continuous Integration (CI) dan Analisis Log Workflow}

\par Untuk menjamin kualitas mutu perangkat lunak serta mencegah masuknya kode yang rusak atau tidak terstandarisasi ke dalam \textit{main branch}, repositori diintegrasikan dengan sistem \textit{Continuous Integration} (CI) berbasis GitHub Actions. Konfigurasi otomasi didefinisikan pada berkas \texttt{.github/workflows/ci.yml} sebagaimana disajikan pada Kode \ref{lst:ci-workflow}.

\begin{lstlisting}[language=yaml, caption={Konfigurasi Otomasi CI GitHub Actions (\texttt{.github/workflows/ci.yml})}, label={lst:ci-workflow}]
name: CI

on:
  push:
    branches: ['main', 'dev', 'feature/**']
  pull_request:
    branches: ['main', 'dev']

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.4'
      - run: composer install --no-progress --no-interaction
      - run: cp .env.example .env
      - run: php artisan key:generate
      - run: php artisan migrate --seed
      - run: php artisan test

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: shivammathur/setup-php@v2
        with:
          php-version: '8.4'
      - run: composer install --no-progress --no-interaction
      - run: vendor/bin/pint --test
\end{lstlisting}

\par Berdasarkan sintaks pada Kode \ref{lst:ci-workflow}, berikut adalah penjelasan dari eksekusi kode per barisnya:
\begin{itemize}
    \item \texttt{name: CI}: Menetapkan label penamaan alur kerja otomasi integrasi berkelanjutan sebagai "CI".
    \item \texttt{on: push: branches: ...} dan \texttt{pull\_request: ...}: Mendefinisikan aturan pemicu (\textit{triggers}) otomatis yang akan mengaktifkan workflow setiap kali terjadi peristiwa \textit{push} ke \textit{branch} \texttt{main}, \texttt{dev}, atau \textit{feature branch} (\texttt{feature/**}), serta saat pembukaan \textit{pull request} ke \textit{branch} \texttt{main} dan \texttt{dev}.
    \item \texttt{jobs: test}: Mendefinisikan \textit{job} pengujian fungsional aplikasi pada lingkungan virtual \texttt{ubuntu-latest}.
    \item \texttt{actions/checkout@v4}: Mengunduh dan menyalin kode sumber repositori ke dalam mesin virtual runner GitHub.
    \item \texttt{setup-php@v2} (PHP 8.4): Mempersiapkan lingkungan eksekusi PHP versi 8.4 beserta ekstensi yang dipersyaratkan oleh Laravel.
    \item \texttt{composer install}: Mengunduh dan menginstal seluruh pustaka dependensi PHP yang terdaftar pada \texttt{composer.json} secara otomatis tanpa prompt interaktif.
    \item \texttt{cp .env.example .env}: Menyalin template konfigurasi variabel lingkungan untuk pengujian CI.
    \item \texttt{php artisan key:generate}: Membuat kunci enkripsi aplikasi unik pada berkas konfigurasi \texttt{.env}.
    \item \texttt{php artisan migrate --seed}: Mengeksekusi migrasi skema tabel ke basis data SQLite virtual dan mengisi data awal (\textit{seeding}).
    \item \texttt{php artisan test}: Menjalankan seluruh pengujian unit dan fitur bawaan Laravel untuk memverifikasi fungsionalitas aplikasi.
    \item \texttt{jobs: lint}: Mendefinisikan \textit{job} kedua untuk memverifikasi kerapian dan standar format kode sumber (\textit{code style}).
    \item \texttt{vendor/bin/pint --test}: Menjalankan perkakas linter Laravel Pint dalam mode pengujian (\texttt{--test}) untuk memastikan seluruh berkas PHP mematuhi standar PSR-12 dan konvensi resmi Laravel.
\end{itemize}

\subsection{Tugas 2: Perancangan Pipeline Multi-Stage CI/CD Empat Tahap}

\par Berdasarkan ketentuan penugasan langkah kedua, alur kerja otomasi GitHub Actions dirancang berupa \textit{multi-stage workflow} empat tahap yang saling terikat secara sekuensial menggunakan direktif \texttt{needs:}:
\begin{center}
    \textbf{Build} $\longrightarrow$ \textbf{Test} $\longrightarrow$ \textbf{Staging} $\longrightarrow$ \textbf{Production}
\end{center}

\par Rantai ketergantungan ini menjamin bahwa suatu tahapan hanya akan dieksekusi jika seluruh tahapan prasyarat sebelumnya telah tuntas dan berstatus \textit{passed}. Konfigurasi alur kerja didefinisikan pada berkas \texttt{.github/workflows/ci.yml} sebagaimana tercantum pada Kode \ref{lst:workflow-ci-cd}.

\begin{lstlisting}[language=yaml, caption={Konfigurasi Lengkap Alur Kerja Multi-Stage CI/CD (\texttt{.github/workflows/ci.yml})}, label={lst:workflow-ci-cd}]
name: CI/CD Pipeline

on:
  push:
    branches: ['main', 'dev', 'feature/**', 'chore/**']
  pull_request:
    branches: ['main']

jobs:
  build:
    name: Build
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup PHP
        uses: shivammathur/setup-php@v2
        with:
          php-version: '8.4'

      - name: Install Dependencies
        run: composer install --no-progress --no-interaction

  test:
    name: Test
    needs: [build]
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup PHP
        uses: shivammathur/setup-php@v2
        with:
          php-version: '8.4'

      - name: Install Dependencies
        run: composer install --no-progress --no-interaction

      - name: Prepare Environment
        run: cp .env.example .env

      - name: Generate Application Key
        run: php artisan key:generate

      - name: Run Tests
        run: php artisan test

      - name: Code Style Check (Pint)
        run: vendor/bin/pint --test

  staging:
    name: Staging
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to Staging
        run: |
          echo "=== MEMULAI DEPLOYMENT KE ENVIRONMENT STAGING ==="
          echo "Menyiapkan rilis aplikasi ke server staging..."
          echo "Simulasi zero-downtime symlink swap pada server staging berhasil."
          echo "Staging deployment selesai tanpa kendala."

  production:
    name: Production
    needs: [staging]
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    environment: production
    steps:
      - name: Execute 7 Steps of deploy.sh
        run: |
          echo "=== MEMULAI DEPLOYMENT KE SERVER PRODUKSI ==="
          echo "Langkah 1: Kunci pintu -- tampilkan halaman pemeliharaan"
          echo "Command: php artisan down --retry=60"
          echo "Langkah 2: Ambil kode terbaru dari repository"
          echo "Command: git pull origin main"
          echo "Langkah 3: Pasang dependensi (tanpa paket dev)"
          echo "Command: composer install --no-dev --optimize-autoloader"
          echo "Langkah 4: Ubah skema basis data, --force = jangan tanya"
          echo "Command: php artisan migrate --force"
          echo "Langkah 5: Bangun ulang cache dengan kode & config baru"
          echo "Command: php artisan config:cache"
          echo "Command: php artisan route:cache"
          echo "Command: php artisan view:cache"
          echo "Langkah 6: Muat ulang pekerja antrean"
          echo "Command: php artisan queue:restart"
          echo "Langkah 7: Buka pintu kembali"
          echo "Command: php artisan up"
          echo "=== DEPLOYMENT PRODUKSI SELESAI DENGAN SUKSES ==="
\end{lstlisting}

\par Penjelasan fungsional dari masing-masing job pada pipeline di atas diuraikan sebagai berikut:
\begin{enumerate}[label=\alph*.]
    \item \textbf{Job \texttt{build}}: Berfungsi menyalin basis kode via \texttt{actions/checkout@v4}, menyiapkan runtime PHP 8.4 via \texttt{setup-php@v2}, serta mengunduh seluruh dependensi paket melalui perintah \texttt{composer install} secara non-interaktif. Langkah ini memastikan keterpenuhan pustaka tanpa hambatan.
    \item \textbf{Job \texttt{test}}: Bergantung pada penyelesaian build (\texttt{needs: [build]}). Job ini menyalin konfigurasi \texttt{.env}, membangkitkan \textit{APP\_KEY}, menjalankan seluruh pengujian otomatis via \texttt{php artisan test}, serta memeriksa kepatuhan standar kode PSR-12 dengan perkakas \texttt{vendor/bin/pint --test}.
    \item \textbf{Job \texttt{staging}}: Terikat dengan deklarasi \texttt{needs: [test]}. Sesuai instruksi penugasan, deployment ke server aktual belum dilakukan, melainkan diekspresikan melalui serangkaian perintah \texttt{echo} yang merepresentasikan simulasi persiapan rilis dan pengujian pada \textit{staging environment}.
    \item \textbf{Job \texttt{production}}: Terikat dengan deklarasi \texttt{needs: [staging]}. Job ini merepresentasikan puncak alur \textit{continuous delivery}, yang mencetak urutan 7 langkah eksekusi deployment standar Laravel secara terstruktur.
\end{enumerate}

\subsection{Tugas 2: Implementasi Script Deployment (\texttt{deploy.sh}) dan 7 Langkah Eksekusi Produksi}

\par Berdasarkan instruksi langkah keempat dan materi kuliah (Slide 6), proses deployment aplikasi Laravel pada server produksi diotomatisasikan melalui skrip shell \texttt{deploy.sh} yang disimpan pada direktori akar repositori. Skrip ini wajib menyertakan flag pengaman \texttt{set -e} pada baris awal untuk memastikan bahwa eksekusi skrip segera berhenti secara \textit{fail-fast} apabila terdapat salah satu perintah yang menghasilkan \textit{non-zero exit code}. Berkas skrip \texttt{deploy.sh} disajikan secara lengkap pada Kode \ref{lst:deploy-sh}.

\begin{lstlisting}[language=bash, caption={Skrip Otomasi Deployment Produksi (\texttt{deploy.sh})}, label={lst:deploy-sh}]
#!/usr/bin/env bash
set -e # berhenti bila ada perintah gagal

cd /var/www/aplikasi

# 1 . Kunci pintu -- tampilkan halaman pemeliharaan
php artisan down --retry=60

# 2 . Ambil kode terbaru
git pull origin main

# 3 . Pasang dependensi (tanpa paket dev)
composer install --no-dev --optimize-autoloader

# 4 . Ubah skema basis data, --force = jangan tanya
php artisan migrate --force

# 5 . Bangun ulang cache dengan kode & config baru
php artisan config:cache
php artisan route:cache
php artisan view:cache

# 6 . Muat ulang pekerja antrean
php artisan queue:restart

# 7 . Buka pintu kembali
php artisan up
\end{lstlisting}

\par Rincian tujuh langkah deployment standar industri pada Kode \ref{lst:deploy-sh} memiliki rasional teknis sebagai berikut:
\begin{enumerate}[label=\arabic*.]
    \item \textbf{Langkah 1 -- Kunci Pintu} (\texttt{php artisan down --retry=60}):\\
          Mengaktifkan \textit{maintenance mode}. Parameter \texttt{--retry=60} menginstruksikan peramban klien untuk mencoba memuat ulang setelah 60 detik agar pengguna tidak menemui error saat pembaruan berlangsung.
    \item \textbf{Langkah 2 -- Ambil Kode Terbaru} (\texttt{git pull origin main}):\\
          Mengunduh seluruh berkas kode sumber terbaru dari branch utama (\texttt{main}) ke direktori kerja server produksi.
    \item \textbf{Langkah 3 -- Pasang Dependensi Produksi}:\\
          Mengeksekusi perintah \texttt{composer install --no-dev --optimize-autoloader}. Langkah ini memasang pustaka tanpa paket pengembangan lokal sekaligus mengoptimasi \textit{classmap autoloader} demi akselerasi performa.
    \item \textbf{Langkah 4 -- Ubah Skema Basis Data} (\texttt{php artisan migrate --force}):\\
          Mengeksekusi penambahan atau pembaruan skema tabel ke basis data produksi. Pada lingkungan \textit{production}, Laravel secara bawaan memunculkan prompt konfirmasi untuk mencegah kehilangan data; flag \texttt{--force} digunakan agar otomasi CI/CD berjalan mandiri tanpa intervensi manual.
    \item \textbf{Langkah 5 -- Bangun Ulang Cache Sistem}:\\
          Membangun berkas tunggal terkompilasi untuk konfigurasi, \textit{routing}, dan template tampilan Blade melalui eksekusi berurutan: \texttt{config:cache}, \texttt{route:cache}, dan \texttt{view:cache}. Langkah ini mengeliminasi pembacaan berkas secara berulang dari disk pada setiap permintaan HTTP yang masuk.
    \item \textbf{Langkah 6 -- Restart Queue Worker} (\texttt{php artisan queue:restart}):\\
          Memerintahkan proses \textit{queue worker} di latar belakang untuk melakukan \textit{graceful stop} dan memuat ulang kode aplikasi terbaru ke memori kerja.
    \item \textbf{Langkah 7 -- Buka Pintu Kembali} (\texttt{php artisan up}):\\
          Menonaktifkan \textit{maintenance mode} dan membuka kembali akses publik aplikasi secara penuh kepada seluruh pengguna.
\end{enumerate}

\par Pada alur kerja GitHub Actions, seluruh langkah di atas dicetak secara berurutan dalam job \texttt{production} menggunakan perintah \texttt{echo} sebagaimana disajikan pada Kode \ref{lst:workflow-ci-cd} baris 72--92.

\subsection{Tugas 2: Proteksi Lingkungan Produksi via Branch Condition dan Environment Reviewer}

\par Sesuai dengan instruksi langkah ketiga, integritas lingkungan produksi harus dijaga melalui dua lapis proteksi utama:
\begin{enumerate}[label=\arabic*.]
    \item \textbf{Kondisi Branch (Ekspresi \texttt{if})}:\\
          Pada definisi job \texttt{production}, disematkan ekspresi kondisional:
          \begin{center}
              \texttt{if: github.ref == 'refs/heads/main'}
          \end{center}
          Aturan ini menegaskan bahwa job \texttt{production} hanya memiliki izin eksekusi apabila peristiwa \textit{push} terjadi langsung pada branch utama (\texttt{main}). Apabila pengembang melakukan \textit{push} ke branch fitur (\texttt{feature/link}) maupun branch eksperimen (\texttt{chore/ci}), job \texttt{build}, \texttt{test}, dan \texttt{staging} tetap berjalan normal untuk menguji integritas kode, namun job \texttt{production} secara otomatis di-\textit{skip}.
    \item \textbf{Proteksi Environment GitHub via Required Reviewers}:\\
          Job \texttt{production} dikaitkan dengan lingkungan terproteksi melalui klausa:
          \begin{center}
              \texttt{environment: production}
          \end{center}
          Pada tingkat konfigurasi repositori GitHub (\textit{Settings} $\rightarrow$ \textit{Environments} $\rightarrow$ \textit{production}), aturan \textit{Deployment protection rules} diaktifkan dengan opsi \textit{Required reviewers}. Melalui mekanisme ini, sekalipun sebuah commit telah berada di branch \texttt{main}, eksekusi langkah deployment pada job \texttt{production} akan ditahan dalam status \textit{waiting for approval} hingga peninjau yang berwenang memberikan persetujuan eksplisit. Hal ini mencegah rilis tidak sengaja ke sistem produksi kritis.
\end{enumerate}

\subsubsection{Konfigurasi Routing dan Controller API}
\par Definisi \textit{route} antarmuka data diatur pada berkas \texttt{routes/api.php} menggunakan kelompok penamaan \textit{route} \texttt{api.} sebagaimana ditunjukkan pada Kode \ref{lst:routes-api}.

\begin{lstlisting}[language=php, caption={[Definisi Endpoint REST API]{Definisi Endpoint REST API pada \texttt{routes/api.php}}}, label={lst:routes-api}]
<?php

use App\Http\Controllers\Api\LinkController;
use Illuminate\Support\Facades\Route;

Route::name('api.')->group(function () {
    Route::get('/links/stats/count', [LinkController::class, 'stats'])->name('links.stats');
    Route::post('/links/shorten', [LinkController::class, 'shorten'])->name('links.shorten');
    Route::apiResource('links', LinkController::class);
});
\end{lstlisting}

\par Berdasarkan Kode \ref{lst:routes-api}, registrasi \textit{route} melalui perintah \texttt{Route::apiResource('links', LinkController::class)} secara otomatis mendaftarkan lima operasi standar CRUD tanpa menyertakan \textit{route} formulir HTML (\texttt{create} dan \texttt{edit}), yaitu:
\begin{itemize}[leftmargin=*]
    \item \texttt{GET /api/links}: Mengambil seluruh koleksi data tautan aktif dan nonaktif dalam format JSON.
    \item \texttt{POST /api/links}: Menyimpan entitas tautan baru ke basis data dengan validasi masukan.
    \item \texttt{GET /api/links/\{id\}}: Mengambil rincian data satu entitas tautan spesifik.
    \item \texttt{PUT/PATCH /api/links/\{id\}}: Memperbarui data entitas tautan yang telah ada.
    \item \texttt{DELETE /api/links/\{id\}}: Menghapus data entitas tautan dari basis data.
\end{itemize}

\par Selain itu, disediakan \textit{route} pendukung \texttt{GET /api/links/stats/count} untuk rekapitulasi jumlah tautan aktif serta total tautan, dan \texttt{POST /api/links/shorten} untuk pemendekan instan. Pada sisi \textit{controller}, kelas \texttt{LinkController} memanfaatkan \texttt{LinkResource} guna memastikan struktur \textit{payload} JSON konsisten serta terisolasi dari tabel internal, seperti disajikan pada Kode \ref{lst:link-controller-api}.

\begin{lstlisting}[language=php, caption={[Controller API \texttt{LinkController.php}]{Implementasi Controller API pada \texttt{app/Http/Controllers/Api/LinkController.php}}}, label={lst:link-controller-api}]
namespace App\Http\Controllers\Api;

use App\Http\Controllers\Controller;
use App\Http\Requests\Api\StoreLinkRequest;
use App\Http\Requests\Api\UpdateLinkRequest;
use App\Http\Resources\ApiResource;
use App\Http\Resources\ApiResourceCollection;
use App\Http\Resources\LinkResource;
use App\Models\Link;
use Illuminate\Http\JsonResponse;

class LinkController extends Controller
{
    public function index(): JsonResponse
    {
        $links = Link::latest()->get();
        return (new ApiResourceCollection(
            LinkResource::collection($links),
            'Berhasil mengambil daftar tautan'
        ))->response();
    }

    public function store(StoreLinkRequest $request): JsonResponse
    {
        $link = Link::create($request->validated());
        return (new ApiResource($link, 'Tautan berhasil ditambahkan', 201))
            ->response()
            ->setStatusCode(201);
    }
}
\end{lstlisting}

\par Berdasarkan Kode \ref{lst:link-controller-api}, seluruh respon dibungkus dalam format JSON terstandarisasi yang memuat atribut status, pesan konfirmasi, serta data \textit{payload}. Pola ini memudahkan lapisan klien dalam memproses hasil respon maupun mendeteksi galat secara seragam.

\subsubsection{Pengelolaan Kebijakan Cross-Origin Resource Sharing (CORS)}
\par Ketika aplikasi web antarmuka pengguna dijalankan pada server pengembangan Vite (berjalan pada alamat \texttt{http://localhost:5173}) dan mencoba melakukan permintaan data ke server Laravel (berjalan pada alamat \texttt{http://localhost:8000}), peramban web secara otomatis menerapkan mekanisme pengamanan \textit{Same-Origin Policy} (SOP). Perbedaan nomor \textit{port} antara \textit{origin} pemanggil dan tujuan permintaan mengharuskan server tujuan mengizinkan \textit{Cross-Origin Resource Sharing} (CORS).

\par Pada kerangka kerja Laravel 11, mekanisme penanganan CORS ditangani secara bawaan oleh \textit{middleware} \texttt{HandleCors} (\texttt{Illuminate\textbackslash Http\textbackslash Middleware\textbackslash HandleCors}) yang terpasang pada tumpukan \textit{middleware} global aplikasi pada penanganan permintaan berkas \texttt{bootstrap/app.php}. Ketika permintaan HTTP metode \texttt{OPTIONS} (\textit{preflight request}) atau permintaan HTTP biasa dikirim oleh klien Vue, \textit{middleware} ini secara otomatis menyertakan tajuk respon keamanan:
\begin{itemize}[leftmargin=*]
    \item \textbf{\texttt{Access-Control-Allow-Origin}}: Mengizinkan domain asal klien (\texttt{http://localhost:5173}) untuk mengakses sumber daya data.
    \item \textbf{\texttt{Access-Control-Allow-Methods}}: Mengizinkan metode HTTP yang digunakan mencakup \texttt{GET, POST, PUT, PATCH, DELETE, OPTIONS}.
    \item \textbf{\texttt{Access-Control-Allow-Headers}}: Mengizinkan tajuk kustom seperti \texttt{Content-Type}, \texttt{Accept}, dan \texttt{Authorization}.
\end{itemize}
Konfigurasi ini memastikan aplikasi antarmuka Vue 3 pada komputer lokal dapat berinteraksi dengan API Laravel secara mulus tanpa terblokir oleh kendala CORS.

\par Sesuai batasan penugasan, alamat URL server API tidak boleh di-\textit{hardcode} di dalam kode program, melainkan wajib diambil secara dinamis dari variabel lingkungan \texttt{VITE\_API\_URL}. \begin{lstlisting}[language=JavaScript, caption={[Pembacaan Environment API]{Pembacaan Variabel Lingkungan API pada \texttt{frontend/src/services/api.ts}}}, label={lst:env-service-api}]
export function getBaseApiUrl(): string {
  // Mengambil URL API secara dinamis dari variabel lingkungan Vite
  const envUrl = import.meta.env.VITE_API_URL
  if (!envUrl) {
    // Nilai fallback yang aman untuk lingkungan pengembangan lokal
    return 'http://localhost:8000/api'
  }
  return envUrl.replace(/\/+$/, '')
}
\end{lstlisting}

\par Berdasarkan Kode \ref{lst:env-service-api}, fungsi \texttt{getBaseApiUrl()} bertugas membaca konfigurasi lingkungan \texttt{import.meta.env.VITE\_API\_URL} yang disediakan oleh mesin Vite saat proses kompilasi maupun saat server pengembang dijalankan. Apabila variabel lingkungan tidak terdefinisi (misalnya saat proses pengujian lokal mandiri), fungsi secara cerdas menyediakan mekanisme \textit{fallback} terstandarisasi pada alamat \texttt{http://localhost:8000/api}. \subsection{Tugas 3: Perancangan Pipeline CI/CD Empat Job Frontend pada GitHub Actions}

\par Menjawab butir penugasan ketiga, keempat, dan kelima, repositori dilengkapi dengan konfigurasi pipeline otomasi yang didedikasikan untuk modul antarmuka pengguna pada berkas \texttt{.github/workflows/frontend.yml}. Pipeline ini mengatur \textit{Continuous Integration} (CI) dan \textit{Continuous Delivery} (CD) dengan arsitektur multi-tahap yang aman dan efisien.

\subsubsection{Struktur dan Ketergantungan Antar-Job}
\par Berkas \textit{workflow} otomasi merangkai empat \textit{job} terpisah menggunakan direktif dependensi \texttt{needs:}. Seluruh definisi konfigurasi disajikan secara lengkap pada Kode \ref{lst:workflow-frontend}.

\begin{lstlisting}[language=yaml, caption={[Pipeline Frontend CI/CD]{Konfigurasi Pipeline Frontend CI/CD (\texttt{.github/workflows/frontend.yml})}}, label={lst:workflow-frontend}]
name: Frontend CI/CD Pipeline

on:
  push:
    branches: ['main', 'dev', 'feature/**', 'chore/**']
  pull_request:
    branches: ['main']

jobs:
  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
          cache-dependency-path: frontend/package-lock.json

      - name: Install Dependencies
        working-directory: frontend
        run: npm ci

      - name: Run Linter
        working-directory: frontend
        run: npm run lint

  test:
    name: Unit Test (Vitest)
    needs: [lint]
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
          cache-dependency-path: frontend/package-lock.json

      - name: Install Dependencies
        working-directory: frontend
        run: npm ci

      - name: Run Vitest Unit Tests
        working-directory: frontend
        run: npm run test:unit

  build:
    name: Build Frontend
    needs: [test]
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: 'npm'
          cache-dependency-path: frontend/package-lock.json

      - name: Install Dependencies
        working-directory: frontend
        run: npm ci

      - name: Build Static Files
        working-directory: frontend
        run: npm run build

      - name: Upload Build Artifact
        uses: actions/upload-artifact@v4
        with:
          name: frontend-dist
          path: frontend/dist/
          retention-days: 7

  deploy:
    name: Deploy to Static Hosting
    needs: [build]
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
    steps:
      - name: Download Build Artifact
        uses: actions/download-artifact@v4

          name: frontend-dist

\par Berdasarkan Kode \ref{lst:workflow-frontend}, arsitektur \textit{workflow} dibangun atas prinsip-prinsip rekayasa otomasi penting:
\begin{enumerate}[label=\arabic*.]
    \item \textbf{Penggunaan \texttt{npm ci} dan Mekanisme Caching Dependensi}: Seluruh \textit{job} mengeksekusi instalasi paket dependensi menggunakan perintah \texttt{npm ci} di dalam direktori kerja \texttt{frontend}. Berbeda dengan \texttt{npm install}, perintah \texttt{npm ci} membaca berkas pengunci \texttt{package-lock.json} secara kaku sehingga menjamin integritas dependensi yang identik (\textit{deterministic build}) di lingkungan \textit{runner}. Efisiensi dipercepat dengan konfigurasi \texttt{cache: 'npm'} dan parameter\\
          \texttt{cache-dependency-path} pada aksi \texttt{actions/setup-node@v4}, menghindari pengunduhan ulang paket biner dari \textit{registry} luar pada eksekusi berulang.
    \item \textbf{Rantai Ketergantungan \texttt{needs:}}: Tahapan eksekusi disusun secara sekuensial hierarkis:
          \begin{center}
              \texttt{lint} $\longrightarrow$ \texttt{test (needs: [lint])} $\longrightarrow$ \texttt{build (needs: [test])} $\longrightarrow$ \texttt{deploy (needs: [build])}
          \end{center}
          Struktur ini memastikan bahwa kode yang tidak lolos standar gaya penulisan atau mengandung galat pengujian unit akan langsung dihentikan secara \textit{fail-fast} sebelum proses kompilasi aset statis yang memakan sumber daya komputasi dijalankan.
\end{enumerate}

\subsubsection{Mekanisme Transfer Artefak Tanpa Re-Build (Zero Build on Deploy)}
\par Memenuhi butir penugasan keempat, \textit{job} \texttt{deploy} tidak diperbolehkan menjalankan ulang perintah \texttt{npm run build}. Sebagai gantinya, hasil kompilasi dari \textit{job} \texttt{build} dioper secara utuh menggunakan mekanisme \textit{artifact sharing} GitHub Actions:
\begin{itemize}[leftmargin=*]
    \item Pada \textit{job} \texttt{build}, aksi \texttt{actions/upload-artifact@v4} mengompresi dan mengunggah seluruh isi direktori rilis \texttt{frontend/dist/} ke penyimpanan artefak terkelola GitHub dengan nama \texttt{frontend-dist}.
    \item Pada \textit{job} \texttt{deploy}, aksi \texttt{actions/download-artifact@v4} mengambil artefak \texttt{frontend-dist} tersebut dan mengekstraknya kembali ke direktori \texttt{frontend/dist}.
    \item \textit{Step} selanjutnya mengeksekusi perintah terminal \texttt{ls -la frontend/dist} serta perintah \texttt{find frontend/dist -type f} untuk menampilkan seluruh struktur berkas rilis ke log eksekusi, memverifikasi ketersediaan berkas \texttt{index.html}, aset JavaScript terkompilasi, serta lembar gaya CSS.
\end{itemize}
Mekanisme ini mencerminkan praktik terbaik industri (\textit{Twelve-Factor App}) di mana tahapan \textit{build} dipisahkan secara tegas dari tahapan \textit{deploy}, menjamin bahwa artefak yang diuji di lingkungan simulasi persis sama dengan artefak yang dirilis ke server produksi.

\subsubsection{Aturan Proteksi Lingkungan dan Pembatasan Deploy pada Branch Main}
\par Memenuhi butir penugasan kelima, pengamanan eksekusi diterapkan pada tingkat deklarasi \textit{job} \texttt{deploy} dengan menyertakan ekspresi kondisi:
\begin{center}
    \texttt{if: github.ref == 'refs/heads/main' \&\& github.event\_name != 'pull\_request'}
\end{center}
\par Aturan logika ini memberikan dua tingkat perlindungan:
\begin{itemize}[leftmargin=*]
    \item Apabila terjadi aktivitas \textit{push} pada \textit{branch} fitur (seperti \texttt{feature/vue}), \textit{branch} perbaikan (\texttt{chore/**}), atau \textit{branch} pengembangan (\texttt{dev}), \textit{workflow} tetap menjalankan \textit{job} \texttt{lint}, \texttt{test}, dan \texttt{build} secara lengkap guna memvalidasi kelayakan kode, namun \textit{job} \texttt{deploy} secara otomatis berstatus \textit{skipped}.
    \item Apabila dibuat suatu \textit{Pull Request} (PR) yang menargetkan \textit{branch} \texttt{main}, \textit{workflow} bertindak sebagai \textit{quality gate} dengan menjalankan pemeriksaan kualitas kode dan pengujian unit tanpa memicu proses \textit{deployment}.
    \item \textit{Job} \texttt{deploy} hanya dan hanya akan dieksekusi ketika perubahan telah disetujui dan di-\textit{merge} ke dalam \textit{branch} utama \texttt{main}.
\end{itemize}

\begin{lstlisting}[language=JavaScript, caption={[Utilitas Logika Mandiri]{Fungsi Utilitas Logika Mandiri pada \texttt{frontend/src/utils/linkLogic.ts}}}, label={lst:link-logic-utils}]
export function isValidUrl(url: string): boolean {
  if (!url || typeof url !== 'string') return false
  const trimmed = url.trim()
  try {
    const parsed = new URL(trimmed)
    return parsed.protocol === 'http:' || parsed.protocol === 'https:'
  } catch {
    return false
  }
}

export function isValidAlias(alias: string): boolean {
  if (!alias) return true // alias bersifat opsional
  const regex = /^[a-zA-Z0-9_-]+$/
  return regex.test(alias.trim())
}

export function buildApiUrl(
  base: string,
  endpoint: string,
  params?: Record<string, string | undefined>
): string {
  const cleanBase = (base || '').replace(/\/+$/, '')
  const cleanEndpoint = (endpoint || '').replace(/^\/+|\/+$/g, '')
  const fullUrl = cleanEndpoint ? `${cleanBase}/${cleanEndpoint}` : cleanBase

  if (!params) return fullUrl

  const searchParams = new URLSearchParams()
  for (const [key, value] of Object.entries(params)) {
    if (value !== undefined && value !== null && value !== '') {
      searchParams.append(key, value)
    }
  }

  const queryString = searchParams.toString()
  return queryString ? `${fullUrl}?${queryString}` : fullUrl
}

export function calculateStats(links: LinkItem[]): LinkStats {
  const safeLinks = Array.isArray(links) ? links : []
  const activeCount = safeLinks.filter((item) => item && item.is_active === true).length

  return {
    active_links_count: activeCount,
    total_links_count: safeLinks.length,
  }
}
\end{lstlisting}

\subsection{Tugas 4: Perancangan Berkas Dockerfile dan Analisis Urutan Instruksi}

\par Berkas \texttt{Dockerfile} bertindak sebagai \textit{blueprint} deklaratif yang mendefinisikan seluruh instruksi pembentukan \textit{image container} aplikasi. Dalam praktikum ini, \textit{image} dirancang dengan memperhatikan efisiensi ukuran, keandalan ekstensi, serta optimasi \textit{layer caching} sesuai prinsip rekayasa perangkat lunak modern. Konfigurasi lengkap \texttt{Dockerfile} disajikan pada Kode \ref{lst:dockerfile}.

\lstinputlisting[language=dockerfile, caption={[Konfigurasi Dockerfile Aplikasi Laravel]{Berkas Konfigurasi \texttt{Dockerfile} untuk \textit{Containerization} Aplikasi Laravel 11}}, label={lst:dockerfile}]{resource/Tugas-4/code/Dockerfile}

\par Berdasarkan Kode \ref{lst:dockerfile}, konfigurasi instruksi disusun secara hierarkis dengan rincian teknis sebagai berikut:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Pemilihan \textit{Base Image} Resmi (\texttt{FROM})}: Instruksi baris 1 menggunakan \textit{base image} resmi \texttt{dunglas/frankenphp:1-php8.4}. FrankenPHP merupakan \textit{web server} aplikasi kontemporer berbasis Caddy yang mengintegrasikan \textit{runtime} PHP langsung ke dalam \textit{web server} tanpa memerlukan \textit{daemon} FastCGI (PHP-FPM) dan Nginx terpisah. Hal ini menyederhanakan arsitektur \textit{container} menjadi satu proses tunggal dengan latensi yang sangat rendah.
    \item \textbf{Instalasi Paket Sistem dan Ekstensi PHP (\texttt{RUN})}: Baris 3--15 memasang paket sistem pendukung serta modul inti PHP melalui utilitas \texttt{install-php-extensions}. Ekstensi yang dipasang mencakup \texttt{pdo\_mysql} untuk komunikasi \textit{database} MySQL, \texttt{gd} untuk manipulasi gambar, \texttt{intl} untuk internasionalisasi, \texttt{zip} untuk ekstraksi berkas kompresi, \texttt{bcmath} untuk kalkulasi presisi tinggi, serta \texttt{opcache} dan \texttt{curl} untuk akselerasi eksekusi kode dan komunikasi jaringan.
    \item \textbf{Penyalinan Biner Composer Secara Efisien}: Baris 17 menerapkan teknik \textit{multi-stage build} ringan dengan menyalin biner Composer versi 2 langsung dari \textit{image} resmi \texttt{composer:2} melalui instruksi\\
          \texttt{COPY --from=composer:2 /usr/bin/composer /usr/bin/composer}, sehingga tidak memerlukan instalasi manual yang membebani ukuran \textit{layer}.
    \item \textbf{Pemisahan Instalasi Dependensi Sebelum Kode Aplikasi}: Baris 19--22 menetapkan direktori kerja \texttt{/app}, lalu menyalin \texttt{composer.json} dan \texttt{composer.lock} secara terisolasi sebelum kode program disalin. Perintah\\
          \texttt{composer install --no-dev --no-scripts --no-autoloader --prefer-dist}\\
          dijalankan pada tahap ini. Strategi ini merupakan kunci utama optimasi \textit{layer caching}: dependensi pihak ketiga yang bersifat statis akan tersimpan dalam \textit{layer cache}, sehingga perubahan rutin pada kode program di kemudian hari tidak memicu pengunduhan ulang dependensi dari jaringan eksternal.
    \item \textbf{Penyalinan Kode Aplikasi dan Optimasi \textit{Autoloader}}: Baris 24--28 menyalin seluruh kode sumber aplikasi ke direktori \texttt{/app}, dilanjutkan dengan eksekusi perintah\\
          \texttt{composer dump-autoload --optimize} untuk menghasilkan \textit{classmap} teroptimasi. Selain itu, hak kepemilikan dan izin direktori \texttt{storage} serta \texttt{bootstrap/cache} diserahkan kepada \textit{user} sistem \texttt{www-data:www-data} (mode 775) guna menjamin operasi berkas log dan sesi berjalan lancar tanpa galat \textit{permission denied}.
    \item \textbf{Deklarasi Port dan Titik Masuk Eksekusi}: Baris 30 mendokumentasikan \textit{port} 80 yang diekspos (\texttt{EXPOSE 80}), dan baris 32 menetapkan perintah utama \textit{server} (\texttt{CMD ["frankenphp", "php-server", "--root", "public/"]}) yang langsung menyajikan berkas publik Laravel saat \textit{container} dijalankan.
\end{enumerate}

\subsection{Tugas 4: Konfigurasi Berkas .dockerignore untuk Efisiensi Konteks Build}

\par Berkas \texttt{.dockerignore} berfungsi memfilter berkas dan direktori lokal agar tidak diikutsertakan ke dalam \textit{build context} yang dikirimkan oleh klien ke \textit{container engine}. Tanpa berkas ini, seluruh direktori lokal akan ditransfer secara mentah, yang berakibat pada pembengkakan ukuran \textit{image}, waktu transfer yang lambat, terjadinya \textit{cache invalidation} yang tidak diinginkan, serta potensi kebocoran informasi rahasia. Konfigurasi \texttt{.dockerignore} yang diterapkan disajikan pada Kode \ref{lst:dockerignore}.

\lstinputlisting[language={}, caption={[Aturan Pengecualian .dockerignore]{Konfigurasi Pengecualian \textit{Build Context} pada Berkas \texttt{.dockerignore}}}, label={lst:dockerignore}]{resource/Tugas-4/code/dockerignore}

\par Berdasarkan Kode \ref{lst:dockerignore}, pemfilteran direktori dan berkas dirancang secara komprehensif mencakup:
\begin{itemize}[leftmargin=*]
    \item \texttt{node\_modules} dan \texttt{frontend/node\_modules}:\\
          Mencegah masuknya direktori \textit{package} JavaScript lokal yang berukuran ratusan megabita dan berpotensi memuat biner yang tidak kompatibel dengan lingkungan Linux di dalam \textit{container}.
    \item \texttt{vendor}: Menjamin bahwa \textit{package} PHP lokal milik mesin pengembang tidak menimpa \textit{package} bersih yang diinstalasi secara deterministik di dalam \textit{container} melalui berkas \texttt{composer.lock}.
    \item \texttt{.git} dan \texttt{.gitignore}: Menghilangkan riwayat \textit{commit} internal Git dari \textit{image production} demi mereduksi ukuran \textit{image} serta menjaga keamanan struktur repositori.
    \item \texttt{.env} dan \texttt{.env.*}: Mencegah berkas konfigurasi lokal yang memuat kredensial sensitif (kunci enkripsi, kata sandi \textit{database}) tersimpan secara permanen di dalam \textit{layer image}.
    \item \texttt{storage/logs/*} dan \texttt{storage/framework/*}: Mengeliminasi berkas log, sesi sementara, dan \textit{view cache} lokal \textit{host} agar tidak mengotori instalasi segar di dalam lingkungan \textit{container}.
\end{itemize}

\subsection[Tugas 5: Refaktorisasi Dockerfile Multi-Stage Build]{Tugas 5: Refaktorisasi Dockerfile Menjadi Arsitektur\\ Multi-Stage Build}

\par Pada arsitektur konvensional \textit{single-stage build}, seluruh perkakas pengembangan (\textit{build tools}), pustaka kompilasi, dependensi Composer, serta kode sumber disatukan ke dalam satu \textit{layer} akhir yang sama. Hal ini menyebabkan pembengkakan ukuran \textit{image} dan memperluas bidang serangan (\textit{attack surface}) di lingkungan produksi. Untuk mengatasi kelemahan tersebut, berkas \texttt{Dockerfile} direfaktorisasi menggunakan pola \textit{multi-stage build} yang memisahkan proses menjadi dua tahap terisolasi: tahap pembangun (\textit{builder stage}) dan tahap pelayan runtime (\textit{runner stage}). Konfigurasi lengkap \texttt{Dockerfile} hasil optimasi disajikan pada Kode \ref{lst:dockerfile-multistage}.

\lstinputlisting[language=dockerfile, caption={[Konfigurasi Dockerfile Multi-Stage]{Berkas Konfigurasi \texttt{Dockerfile} dengan Arsitektur Multi-Stage Build, Varian Alpine, User Non-Root, dan Healthcheck}}, label={lst:dockerfile-multistage}]{resource/Tugas-5/Code/Dockerfile}

\par Berdasarkan Kode \ref{lst:dockerfile-multistage}, arsitektur berkas \texttt{Dockerfile} disusun secara modular dengan rincian teknis sebagai berikut:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Tahap 1: Builder (\texttt{AS builder})}:\\
          Instruksi baris 5 menetapkan \textit{base image} pembangun menggunakan distribusi:\\
          \texttt{dunglas/frankenphp:1-php8.4-alpine}. Pada baris 8, biner Composer versi 2 disalin langsung dari \textit{image} resmi \texttt{composer:2} melalui instruksi\\
          \texttt{COPY --from=composer:2 /usr/bin/composer /usr/bin/composer}. Setelah direktori kerja \texttt{/app} ditetapkan, berkas manifes dependensi \texttt{composer.json} dan \texttt{composer.lock} disalin terlebih dahulu (baris 13) sebelum kode aplikasi disalin. Perintah \texttt{composer install} dijalankan pada baris 16--22 dengan parameter produksi yang ketat:
          \begin{itemize}[leftmargin=*]
              \item \texttt{--no-dev}: Mengabaikan instalasi seluruh dependensi pengembangan (seperti PHPUnit, Mockery, Collision, Faker).
              \item \texttt{--no-interaction}: Menonaktifkan interaksi prompt terminal.
              \item \texttt{--no-plugins} dan \texttt{--no-scripts}: Mencegah eksekusi skrip otomatis yang tidak diperlukan pada tahap awal penyusunan dependensi.
              \item \texttt{--prefer-dist} dan \texttt{--no-autoloader}: Mengunduh arsip distribusi dependensi secara cepat tanpa menghasilkan peta \textit{classmap} terlebih dahulu.
          \end{itemize}
          Selanjutnya, baris 25 menyalin seluruh kode sumber aplikasi ke direktori pembangun, disusul pembersihan berkas \textit{cache} sementara dan eksekusi perintah optimasi \textit{autoloader}:\\
          \texttt{composer dump-autoload --optimize --no-dev --no-scripts}\\
          pada baris 28--29 guna menghasilkan berkas \textit{classmap} teroptimasi secara statis.
    \item \textbf{Tahap 2: Runner (\texttt{AS runner})}:\\
          Instruksi baris 37 mendeklarasikan awal tahap runtime baru yang sepenuhnya bersih, kembali menggunakan \textit{base image}\\
          \texttt{dunglas/frankenphp:1-php8.4-alpine}. Biner Composer beserta perkakas pembangun tidak diikutsertakan. Pada baris 40--47, modul inti PHP esensial dipasang untuk melayani \textit{request}, yaitu \texttt{pdo\_mysql}, \texttt{gd}, \texttt{intl}, \texttt{zip}, \texttt{bcmath}, \texttt{opcache}, dan \texttt{curl}.
    \item \textbf{Penyalinan Artefak Bersih (\texttt{COPY --from=builder})}:\\
          Kunci utama efisiensi arsitektur ini terletak pada instruksi baris 52,\\ \texttt{COPY --from=builder /app /app}. Instruksi ini secara selektif hanya menyalin direktori kerja aplikasi yang telah memuat direktori \texttt{vendor} bersih dan kode sumber teroptimasi dari tahap pembangun, tanpa menyertakan artefak kompilasi eksternal maupun biner Composer.
    \item \textbf{Penguncian Versi dan Pemilihan Varian Minimalis}:\\
          Alih-alih menggunakan tag generik \texttt{latest} yang tidak deterministik atau varian berbasis Debian glibc yang berbobot besar, konfigurasi ini secara konsisten mengunci versi rilis pada tag spesifik\\
          \texttt{dunglas/frankenphp:1-php8.4-alpine}. Distribusi Alpine Linux menggunakan pustaka C yang sangat ramping (\textit{musl libc}) dan pengelola paket \texttt{apk}, sehingga fondasi sistem operasi kontainer menjadi sangat minimalis.
\end{enumerate}

\subsection[Tugas 5: Pengerasan Keamanan Non-Root User \& Healthcheck]{Tugas 5: Pengerasan Keamanan Non-Root User\\ dan Monitoring Healthcheck}

\par Standar keamanan industri kontainer mewajibkan penerapan prinsip \textit{Principle of Least Privilege}. Secara bawaan, apabila tidak ditentukan lain, proses di dalam kontainer akan dieksekusi dengan hak istimewa pengguna tertinggi (\texttt{root} dengan UID 0). Kondisi ini sangat berbahaya karena jika terjadi eksploitasi kerentanan keamanan pada aplikasi web (misalnya eksekusi kode berbahaya secara jarak jauh), penyerang berpotensi memperoleh kendali penuh atas sistem kontainer bahkan melakukan pelarian kontainer (\textit{container breakout}) ke mesin \textit{host}.

\par Untuk memitigasi risiko tersebut, pada tahap \textit{runner} berkas \texttt{Dockerfile} disematkan instruksi hak akses dan penetapan pengguna \textit{non-root}:
\begin{lstlisting}[language=dockerfile, caption={[Konfigurasi Hak Akses dan User Non-Root]{Pengaturan Perizinan Direktori dan Instruksi \texttt{USER www-data}}}, label={lst:user-non-root}]
RUN mkdir -p /data/caddy /config/caddy /app/storage /app/bootstrap/cache \
    && rm -f /app/bootstrap/cache/*.php \
    && chown -R www-data:www-data /data/caddy /config/caddy /app/storage /app/bootstrap/cache \
    && chmod -R 775 /app/storage /app/bootstrap/cache

USER www-data
\end{lstlisting}

\par Berdasarkan Kode \ref{lst:user-non-root}, sebelum instruksi \texttt{USER www-data} diaktifkan, direktori kerja Caddy dan direktori aplikasi Laravel yang memerlukan izin tulis (\texttt{storage} untuk berkas log dan sesi, serta \texttt{bootstrap/cache} untuk tembolok rute dan konfigurasi) diserahkan kepemilikannya kepada pengguna dan grup sistem \texttt{www-data:www-data} dengan mode izin \texttt{775}. Setelah izin dipersiapkan, instruksi \texttt{USER www-data} dideklarasikan sehingga seluruh proses runtime FrankenPHP berjalan di bawah konteks pengguna non-istimewa.

\par Pembuktian bahwa kontainer tidak berjalan sebagai pengguna \texttt{root} dibuktikan melalui eksekusi perintah inspeksi pengguna \texttt{whoami} secara langsung ke dalam kontainer yang sedang aktif (\texttt{podman exec kepl-laravel-multistage whoami}), dengan luaran yang disajikan pada Kode \ref{lst:whoami}.

\lstinputlisting[language={}, caption={[Verifikasi Identitas Pengguna Non-Root]{Luaran Eksekusi Perintah \texttt{podman exec whoami} di dalam Container}}, label={lst:whoami}]{resource/Tugas-5/Code/whoami.txt}

\par Berdasarkan Kode \ref{lst:whoami}, sistem secara tegas mengembalikan luaran \texttt{www-data}. Hal ini membuktikan secara mutlak bahwa batas isolasi proses telah terkunci pada pengguna non-root berhak akses terbatas, sehingga persyaratan keamanan kontainer terpenuhi sepenuhnya.

\par Aspek keandalan berikutnya mencakup pengujian ketersediaan layanan melalui instruksi \texttt{HEALTHCHECK}. Pada berkas \texttt{Dockerfile}, instruksi ini dikonfigurasi sebagai berikut:

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://127.0.0.1/api/health || curl -f http://127.0.0.1/ || exit 1
\end{lstlisting}

\par Berdasarkan Kode \ref{lst:healthcheck-cfg}, mekanisme pemantauan kesehatan dikonfigurasi dengan parameter interval pengujian berkala setiap 30 detik (\texttt{--interval=30s}), batas waktu toleransi respons 5 detik (\texttt{--timeout=5s}), masa inisialisasi awal aplikasi 10 detik (\texttt{--start-period=10s}), serta toleransi kegagalan berturut-turut sebanyak 3 kali (\texttt{--retries=3}). Pemeriksaan mengeksekusi utilitas \texttt{curl} untuk meminta endpoint kesehatan \texttt{/api/health} atau rute publik utama \texttt{/}. Status kontainer yang sedang berjalan aktif diperiksa menggunakan perintah \texttt{podman ps}, dengan luaran yang disajikan pada Kode \ref{lst:healthcheck}.

\subsection{Tugas 5: Otomasi Pipeline CI/CD dan Publikasi Image ke GitHub Container Registry (GHCR)}

\par Tahap akhir penugasan adalah mengintegrasikan berkas \texttt{Dockerfile} ke dalam \textit{pipeline} \textit{Continuous Integration and Continuous Deployment} (CI/CD) menggunakan GitHub Actions. Tujuannya adalah mengotomasi proses kompilasi \textit{image} setiap kali terjadi pembaruan kode, serta mempublikasikan \textit{image} yang siap produksi ke registri kontainer resmi GitHub (\textit{GitHub Container Registry} / GHCR pada domain \texttt{ghcr.io}).

\par Sebelum mengeksekusi \textit{workflow}, konfigurasi hak akses keamanan repositori wajib disesuaikan agar token bawaan \texttt{GITHUB\_TOKEN} diizinkan menulis dan memperbarui paket pada registri GHCR. Konfigurasi perizinan repositori tersebut ditunjukkan pada Gambar \ref{fig:konfigurasi-github-actions-permissions}.

\par Berdasarkan Gambar \ref{fig:konfigurasi-github-actions-permissions}, pada menu \textit{Settings} $\rightarrow$ \textit{Actions} $\rightarrow$ \textit{General} bagian \textit{Workflow permissions}, opsi perizinan ditetapkan ke \textbf{\textit{Read and write permissions}}. \par Berkas konfigurasi otomasi \textit{workflow} disimpan pada berkas konfigurasi\\

\par Berdasarkan Kode \ref{lst:docker-publish}, alur kerja otomasi dirancang dengan memperhatikan kaidah rekayasa perangkat lunak modern sebagai berikut:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Pemicu Eksekusi (\textit{Triggers})}: Baris 3--7 mengonfigurasi pemicu \textit{workflow} secara otomatis pada peristiwa \texttt{push} ke \textit{branch} \texttt{main}, \texttt{dev}, serta \textit{branch} fitur (\texttt{feature/**}) dan \textit{branch} pemeliharaan (\texttt{chore/**}), serta pada peristiwa \texttt{pull\_request} menuju \textit{branch} \texttt{main}.
    \item \textbf{Normalisasi Nama Image Menjadi Huruf Kecil (\textit{Lowercase Normalization})}: Registri GHCR menerapkan aturan ketat bahwa nama paket dan organisasi wajib menggunakan huruf kecil semua (\textit{lowercase}). \section{Kesimpulan}

\par Berdasarkan seluruh tahapan konstruksi, implementasi fitur, pengujian empiris, evaluasi keamanan, serta evolusi berkesinambungan yang telah dilaksanakan dari Tugas 1 hingga Tugas 5 pada mata kuliah Konstruksi dan Evolusi Perangkat Lunak, dapat ditarik beberapa kesimpulan komprehensif sebagai berikut:
\begin{enumerate}[leftmargin=*]
    \item \textbf{Capaian Tugas 1 -- Pengelolaan Repositori, Disiplin Commit, dan Otomasi CI}: Repositori publik \texttt{evolusi-pl-24-538699-SV-24524} berhasil diinisialisasi pada organisasi \texttt{KEPL2026} sebagai fondasi proyek web Laravel 11. Penerapan standar \textit{Conventional Commits} secara konsisten menghasilkan rekam jejak semantik yang transparan. Alur \textit{branching} tiga tingkat (\texttt{main}, \texttt{dev}, \texttt{feature}) dipadukan dengan aturan \textit{branch ruleset} dan pembukaan dua \textit{Pull Request} sukses mengisolasi penambahan fitur login dan registrasi. Sistem CI GitHub Actions dengan dua \textit{job} independen (\texttt{test} dan \texttt{lint}) berhasil bertindak sebagai \textit{automated quality gate} pertama.
    \item \textbf{Capaian Tugas 2 -- Evolusi Fungsionalitas CRUD, Pipeline Multi-Stage CD, dan Standarisasi Deployment}: Fungsionalitas aplikasi dievolusikan mencakup operasi CRUD penuh pada tabel \texttt{links} yang teruji 100\% via 13 skenario PHPUnit (34 \textit{assertions}). Perancangan \textit{multi-stage workflow} empat sekuens (\textbf{Build} $\rightarrow$ \textbf{Test} $\rightarrow$ \textbf{Staging} $\rightarrow$ \textbf{Production}) via direktif \texttt{needs:} menjamin integritas berjenjang. Skrip \texttt{deploy.sh} mengotomasi 7 langkah rilis produksi Laravel secara aman dengan proteksi \textit{fail-fast} (\texttt{set -e}). Evaluasi kondisi \texttt{github.ref} dan proteksi \textit{environment} berhasil membatasi \textit{deployment} hanya untuk \textit{branch} \texttt{main}, serta membuktikan ketahanan sistem saat terjadi kegagalan uji coba (status merah) dan pemulihan cepat (status hijau).
    \item \textbf{Capaian Tugas 3 -- Arsitektur RESTful API, Antarmuka Vue 3 SPA, dan Pipeline Frontend}: Lapisan backend dievolusikan menyediakan \textit{endpoint} JSON terstandarisasi melalui \texttt{Route::apiResource} dengan penanganan CORS aktif via middleware \texttt{HandleCors}. Aplikasi antarmuka mandiri dibangun menggunakan Vue 3, Vite, TypeScript, dan Vue Router dengan abstraksi variabel lingkungan dinamis \texttt{VITE\_API\_URL}. Pipeline otomasi frontend mengorkestrasi empat \textit{job} (\textbf{Lint} $\rightarrow$ \textbf{Unit Test} $\rightarrow$ \textbf{Build} $\rightarrow$ \textbf{Deploy}) dengan efisiensi \texttt{npm ci} dan \textit{caching}. Transfer artefak rilis \texttt{dist/} tanpa kompilasi ulang (\textit{zero build on deploy}) berhasil diimplementasikan, didukung 19 kasus pengujian unit mandiri Vitest yang lulus sempurna tanpa dependensi jaringan.
    \item \textbf{Capaian Tugas 4 -- Containerization FrankenPHP, Isolasi Build Context, dan Layer Caching}: Aplikasi web Laravel berhasil dikontainerisasi ke dalam \textit{image} mandiri berbasis server modern FrankenPHP (PHP 8.4) tanpa memerlukan daemon PHP-FPM dan Nginx terpisah. Pengaturan isolasi berkas pada \texttt{.dockerignore} terbukti efektif mencegah masuknya berkas lingkungan sensitif (\texttt{.env}) dan paket berukuran besar (\texttt{vendor}, \texttt{node\_modules}). Strategi penataan instruksi \texttt{Dockerfile} terbukti secara empiris memangkas waktu pembangunan citra dari 141,196 detik pada siklus bersih pertama menjadi 3,731 detik pada siklus ketiga pasca modifikasi kode (peningkatan efisiensi waktu sebesar 97,36\%). Kontainer berhasil berjalan stabil pada \textit{bridge network} dengan pemetaan port 8007, menyajikan antarmuka web dan merespons endpoint \texttt{GET /api/health} (\texttt{200 OK}, 37 ms).
    \item \textbf{Capaian Tugas 5 -- Multi-Stage Build Alpine, Keamanan Non-Root, Healthcheck, dan Publikasi GHCR}: Refaktorisasi berkas \texttt{Dockerfile} menjadi arsitektur \textit{multi-stage build} yang memisahkan tahap \textit{builder} dan \textit{runner}, dipadukan dengan penguncian versi pada distribusi minimalis \texttt{dunglas/frankenphp:1-php8.4-alpine}, terbukti secara empiris memangkas ukuran \textit{image} dari 725 MB menjadi 296 MB (reduksi drastis sebesar 429 MB atau efisiensi 59,17\%). Pengerasan keamanan berhasil diwujudkan melalui pengalihan eksekusi ke pengguna non-root berhak akses terbatas (\texttt{USER www-data}) yang terverifikasi via perintah \texttt{whoami}. Pemantauan kesehatan berkala dikonfigurasi melalui instruksi \texttt{HEALTHCHECK}. Akhirnya, seluruh alur kompilasi dan publikasi \textit{image} terotomasi penuh ke GitHub Container Registry (\texttt{ghcr.io}) via GitHub Actions dengan skema penandaan SHA commit deterministik dan visibilitas paket publik.

\end{enumerate}
