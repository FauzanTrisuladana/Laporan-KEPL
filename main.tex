\subsection{Identitas Repository, Live Deployment, dan Rangkaian Command Eksekusi}

\par Ujian Tengah Semester (UTS) Praktikum Konstruksi dan Evolusi Perangkat Lunak mengintegrasikan seluruh kompetensi rekayasa perangkat lunak ke dalam satu sistem terpadu. Proyek yang dikembangkan mengangkat studi kasus baru yang berbeda dari penugasan mingguan sebelumnya, yaitu \textbf{Sistem Informasi Akuntansi Pemuda (Nogotirto V)}. Sistem ini dirancang untuk mengelola pembukuan keuangan organisasi kepemudaan yang mencakup manajemen kas, pencatatan transaksi pemasukan dan pengeluaran, mutasi antar-rekening, pengelolaan penanggung jawab kegiatan, rekonsiliasi saldo riil harian, hingga ekspor laporan keuangan dalam format PDF.

\par Secara arsitektural, sistem memisahkan \textit{backend} RESTful API berbasis Laravel 12 yang dijalankan di atas \textit{application server} FrankenPHP dengan \textit{frontend} \textit{Single Page Application} (SPA) berbasis Vue.js 3, TypeScript, dan Tailwind CSS di dalam satu \textit{monorepo} publik bernama \texttt{uts-pl-24-538699-SV-24524}. Seluruh siklus pengembangan dikelola menggunakan \textit{Git workflow} dengan \textit{branch protection ruleset}, diotomasi melalui \textit{pipeline} \textit{Continuous Integration} (CI) dan \textit{Continuous Deployment} (CD) pada GitHub Actions, dipublikasikan sebagai \textit{container image} ke GitHub Container Registry (GHCR), serta diorkestrasi menggunakan Podman Compose.

\subsection{Pengembangan Backend RESTful API Berbasis Laravel 12 (Soal 1)}

\par Lapisan \textit{backend} dikembangkan menggunakan Laravel 12 pada direktori \texttt{backend/} untuk menyediakan \textit{service} RESTful API dengan format pertukaran data JSON. Arsitektur berlapis dari sistem \textit{backend} yang dibangun divisualisasikan pada Gambar \ref{fig:arsitektur-backend}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{resource/SS/arsitektur-backend.png}
  \caption{Diagram Layered Architecture Backend RESTful API Laravel 12 dan FrankenPHP}
  \label{fig:arsitektur-backend}
\end{figure}

\par Berdasarkan Gambar \ref{fig:arsitektur-backend}, arsitektur \textit{backend} tersusun atas lima \textit{layer} utama yang saling terintegrasi. \textit{Layer} pertama merupakan konfigurasi \textit{environment} melalui berkas \texttt{.env} yang menyimpan pengaturan koneksi \textit{database}, \textit{encryption key} \texttt{APP\_KEY}, konfigurasi Laravel Sanctum, serta kebijakan \textit{Cross-Origin Resource Sharing} (CORS). \textit{Layer} kedua adalah \textit{HTTP Routing \& Security Layer} yang ditenagai oleh \textit{application server} FrankenPHP dan berkas \texttt{routes/api.php}, dilengkapi proteksi \textit{middleware} \texttt{auth:sanctum} untuk verifikasi token serta \texttt{CheckRole} untuk otorisasi \textit{role} pengguna. \textit{Layer} ketiga memuat sembilan \textit{API Controller} dan \textit{Form Request} yang menangani validasi \textit{input} dengan pengembalian \textit{HTTP status code} \texttt{422} apabila data tidak valid. \textit{Layer} keempat mencakup \textit{model} Eloquent ORM beserta \textit{API Resource} untuk memformat struktur \textit{payload} JSON secara seragam, sedangkan \textit{layer} kelima menangani persistensi data pada \textit{database} MySQL.

\par Implementasi definisi \textit{route} RESTful API pada berkas \texttt{backend/routes/api.php} disajikan pada Kode \ref{lst:api-routes}.

\lstinputlisting[language=PHP, caption={[Konfigurasi Route RESTful API (\texttt{routes/api.php})]{Definisi Endpoint RESTful API dengan Proteksi Middleware Sanctum pada Laravel 12}}, label={lst:api-routes}]{resource/Code/api-routes.php}

\par Berdasarkan Kode \ref{lst:api-routes}, \textit{route} publik \texttt{GET /api/status} disediakan pada baris 16--18 untuk keperluan pemantauan \texttt{healthcheck} \textit{container}. \textit{Route} autentikasi didefinisikan pada grup \textit{prefix} \texttt{auth} (baris 21--26), di mana \texttt{POST /api/auth/login} bersifat terbuka bagi \textit{client} yang mengirimkan kredensial \textit{email} dan \textit{password} untuk memperoleh \textit{Bearer token} Laravel Sanctum, sedangkan \texttt{POST /api/auth/logout} dilindungi oleh \textit{middleware} \texttt{auth:sanctum} untuk mencabut token aktif dari tabel \texttt{personal\_access\_tokens}. Seluruh \textit{route} bisnis lainnya dibungkus di dalam grup \texttt{Route::middleware('auth:sanctum')} (baris 28--70), sehingga setiap \textit{request} tanpa token yang valid akan langsung ditolak dengan \textit{response} JSON berstatus \texttt{401 Unauthorized}. Di dalam grup \textit{middleware} \texttt{role:bendahara}, didefinisikan berbagai \textit{resource route} dengan operasi CRUD lengkap (\texttt{index}, \texttt{show}, \texttt{store}, \texttt{update}, \texttt{destroy}), meliputi \texttt{penanggung-jawab}, \texttt{akun}, \texttt{transaksi}, \texttt{mutasi-rekening}, \texttt{history-riil}, dan \texttt{user}.

\par Pengujian fungsional seluruh \textit{endpoint} dilakukan menggunakan \textit{HTTP client} Hoppscotch. Hasil eksekusi \textit{request} beserta struktur pengorganisasian \textit{API collection} ditunjukkan pada Gambar \ref{fig:pengujian-api-hoppscotch}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{resource/SS/pengujian-api-hoppscotch.png}
  \caption{Pengujian Endpoint RESTful API dan Request Collection pada Antarmuka Hoppscotch}
  \label{fig:pengujian-api-hoppscotch}
\end{figure}

\par Berdasarkan Gambar \ref{fig:pengujian-api-hoppscotch}, \textit{request collection} bernama \texttt{KEPL-UTS} memiliki folder autentikasi (\texttt{Login} dan \texttt{Logout}) serta folder \texttt{(Auth)} yang memuat seluruh modul fungsional, meliputi manajemen profil, pengguna, penanggung jawab, riwayat riil, akun keuangan, mutasi rekening, transaksi, laporan, dan ringkasan \textit{dashboard}. Ketika \textit{request} pengambilan daftar penanggung jawab dieksekusi dengan menyertakan \textit{Bearer token} pada \textit{header} \texttt{Authorization}, \textit{server} merespons dengan \textit{status code} \texttt{200 OK} dalam waktu 39 milidetik dan mengirimkan \textit{payload} JSON berisi daftar objek penanggung jawab dari \textit{database}. Seluruh \textit{collection} ini telah diekspor ke dalam berkas \texttt{all-collection.json} serta \texttt{collection-env.json} pada folder \texttt{hoppscotch-collection} di direktori dokumentasi \textit{repository}, sehingga dapat diimpor langsung ke dalam Hoppscotch maupun Postman.

\par Untuk menjamin keandalan setiap \textit{endpoint} terhadap perubahan kode, disusun rangkaian \textit{feature test} otomatis berbasis PHPUnit pada direktori \texttt{backend/tests/Feature/}. Secara keseluruhan terdapat 11 berkas \textit{feature test}, dengan dua sampel utama yaitu \texttt{AuthTest.php} dan \texttt{AkunTest.php} sebagaimana ditampilkan pada Kode \ref{lst:auth-test} serta Kode \ref{lst:akun-test}.

\lstinputlisting[language=PHP, caption={[Feature Test Autentikasi API (\texttt{AuthTest.php})]{Implementasi Feature Test untuk Skenario Login, Validasi 422, Penolakan 401, dan Logout}}, label={lst:auth-test}]{resource/Code/auth-test.php}

\par Berdasarkan Kode \ref{lst:auth-test}, kelas \texttt{AuthTest} memanfaatkan \textit{trait} \texttt{RefreshDatabase} agar setiap \textit{test case} dieksekusi pada skema \textit{database} SQLite \textit{in-memory} yang terisolasi. Metode pengujian memverifikasi lima \textit{test case} utama: keberhasilan \textit{login} yang mengembalikan \textit{status code} \texttt{200} beserta struktur token Sanctum (baris 13--40), penolakan \textit{login} dengan \textit{password} salah yang mengembalikan \textit{status code} \texttt{401} (baris 42--58), kegagalan validasi \textit{input} yang mengembalikan \textit{status code} \texttt{422} beserta rincian \textit{error} atribut (baris 60--70), keberhasilan pencabutan token saat \textit{logout} (baris 72--87), serta pemblokiran akses \textit{logout} tanpa token dengan \textit{status code} \texttt{401} (baris 89--96).

\lstinputlisting[language=PHP, caption={[Feature Test CRUD Akun Keuangan (\texttt{AkunTest.php})]{Implementasi Feature Test untuk Operasi Index, Store (201), Show, Update, dan Destroy pada Resource Akun}}, label={lst:akun-test}]{resource/Code/akun-test.php}

\par Berdasarkan Kode \ref{lst:akun-test}, kelas \texttt{AkunTest} menguji siklus operasi CRUD lengkap pada \textit{endpoint} \texttt{/api/akun}. Fungsi bantuan \texttt{getBendaharaToken()} membuat data \textit{user} aktif ber-\textit{role} \texttt{bendahara} serta mencetak token Sanctum untuk disertakan pada \textit{header} \texttt{Authorization}. Rangkaian \textit{assertion} memvalidasi pengambilan daftar akun dengan filter kas (\texttt{200 OK}), pembuatan akun baru melalui \texttt{postJson('/api/akun')} yang menghasilkan \textit{status code} \texttt{201 Created} sekaligus memverifikasi keberadaan baris data di tabel \texttt{akun} melalui \texttt{assertDatabaseHas} (baris 43--64), pengambilan detail satu akun (\texttt{getJson}), pembaruan data akun (\texttt{putJson}), hingga penghapusan akun (\texttt{deleteJson}) yang terverifikasi melalui \texttt{assertSoftDeleted}.

\begin{figure}[H]

\subsection{Analisis Aliran Data End-to-End serta Kendala dan Solusi Teknis (Soal 8)}

\subsubsection{Penjelasan Aliran Data End-to-End dari Vue.js ke Laravel hingga Database}

\par Aliran data secara \textit{end-to-end} di dalam ekosistem \textit{multi-container} yang telah dibangun berlangsung melalui tahapan berurutan sebagai berikut:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Inisiasi Request dari Komponen View Vue.js}: Saat pengguna berinteraksi pada halaman aplikasi di \textit{browser}, seperti menekan tombol \textit{login} atau menyimpan data baru, komponen \textit{view} pada folder \texttt{src/views/} akan memanggil fungsi \textit{service} asinkron di dalam direktori \texttt{src/services/}.
  \item \textbf{Penyematan Token oleh Request Interceptor Axios}: Modul \textit{service} meneruskan pemanggilan ke instans \textit{HTTP client} Axios terpusat (\texttt{src/services/api.ts}). Sebelum paket HTTP keluar dari \textit{browser}, \textit{request interceptor} mengambil token Sanctum dari \texttt{localStorage}, menyematkan nilai \texttt{Bearer <token>} pada \textit{header} \texttt{Authorization}, lalu mengirimkan \textit{request} tersebut ke \textit{path} relatif \texttt{/api/...} sesuai konfigurasi \texttt{VITE\_API\_URL=/api}.
  \item \textbf{Penerimaan dan Reverse Proxy pada Container Nginx}: \textit{HTTP request} diterima oleh \textit{container} \texttt{uts-kepl-frontend} yang menjalankan Nginx 1.27 Alpine. Karena URL \textit{request} diawali dengan \textit{prefix} \texttt{/api/}, konfigurasi pada berkas \texttt{nginx.conf} meneruskan paket data tersebut menggunakan mekanisme \textit{reverse proxy} menuju alamat internal \textit{service} \texttt{backend} pada \textit{port} 80 melalui \textit{bridge network} \texttt{kepl}.
  \item \textbf{Pemrosesan Request oleh FrankenPHP dan Middleware Laravel}: DNS internal pada \textit{network} \texttt{kepl} meresolusi \textit{hostname} \texttt{backend} ke alamat IP \textit{container} \texttt{uts-kepl-backend}. \textit{Application server} FrankenPHP yang mendengarkan pada \textit{port} 80 menerima \textit{request} tersebut dan meneruskannya ke \textit{entry point} \texttt{public/index.php} milik Laravel 12. Kernel HTTP Laravel mengarahkan \textit{request} ke berkas \texttt{routes/api.php}, memverifikasi validitas \textit{Bearer token} melalui \textit{middleware} \texttt{auth:sanctum}, serta memeriksa otorisasi \textit{role} melalui \textit{middleware} \texttt{role:bendahara}.
  \item \textbf{Validasi Input dan Eksekusi Eloquent ORM ke MySQL}: Setelah melewati lapisan \textit{middleware}, data \textit{request} divalidasi oleh kelas \textit{Form Request} (mengembalikan \textit{response} JSON \texttt{422} jika tidak valid) dan diproses oleh metode \textit{Controller}. \textit{Controller} memanggil \textit{model} Eloquent ORM yang membuka koneksi PDO ke \textit{container database} \texttt{uts-kepl-mysql} menggunakan \textit{hostname} \texttt{db} dan \textit{port} internal \texttt{3306}.
  \item \textbf{Persistensi pada Named Volume dan Pengembalian Response JSON}: Mesin \textit{database} MySQL mengeksekusi \textit{query} SQL dan menyimpan perubahan data secara fisik ke dalam \textit{named volume} \texttt{kepl\_mysql\_data}. Hasil \textit{query} dikembalikan ke Eloquent ORM, diformat oleh \textit{Controller} menjadi \textit{payload} JSON terstandarisasi dengan \textit{HTTP status code} yang sesuai (\texttt{200 OK} atau \texttt{201 Created}), lalu dikirimkan kembali melewati FrankenPHP dan Nginx menuju Axios di \textit{browser} untuk memperbarui \textit{state} tampilan secara reaktif.
\end{enumerate}

\subsubsection{Kendala yang Ditemui dan Cara Mengatasinya}

\par Selama proses pengembangan, \textit{containerization}, dan konfigurasi otomasi CI/CD, ditemukan empat kendala teknis utama beserta langkah penyelesaiannya sebagai berikut:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Resolusi Internal Container Port vs Host Port pada Orkestrasi Compose}:\\
        \textit{Kendala}: Pada mesin lokal, \textit{port} bawaan MySQL yaitu \texttt{3306} telah digunakan oleh \textit{service} lain sehingga pemetaan \textit{host port} pada \textit{service} \texttt{db} dialihkan ke \texttt{3307:3306}. Pada konfigurasi awal, \textit{environment variable} \texttt{DB\_PORT} dan \texttt{PMA\_PORT} sempat diisi dengan nilai \texttt{3307}, yang mengakibatkan \textit{service backend} maupun phpMyAdmin mengalami \textit{connection refused} saat menghubungi \textit{database}.\\
        \textit{Cara Mengatasi}: Dilakukan pemisahan antara \textit{host port} eksternal dan \textit{container port} pada \textit{network} internal. Di dalam \textit{bridge network} \texttt{kepl}, \textit{container} MySQL tetap mendengarkan pada \textit{port} internal \texttt{3306}. Oleh karena itu, nilai \texttt{DB\_PORT} pada \textit{service} \texttt{backend} serta \texttt{PMA\_PORT} pada \textit{service} \texttt{phpmyadmin} dikembalikan ke \texttt{3306} dengan \texttt{DB\_HOST: db}, sedangkan pemetaan \texttt{3307:3306} hanya digunakan pada bagian \texttt{ports} untuk akses dari mesin \textit{host}.
  \item \textbf{Ketiadaan Binary \texttt{curl} Bawaan pada Base Image \texttt{nginx:1.27-alpine}}:\\
        \textit{Kendala}: Ketika konfigurasi \texttt{healthcheck} untuk \textit{container} \texttt{uts-kepl-frontend} ditambahkan pada berkas \texttt{compose.yml} menggunakan \textit{command} \texttt{curl -f http://localhost/}, status \textit{container} tersebut sempat menjadi \texttt{unhealthy} karena \textit{base image} minimalis Nginx Alpine belum menyertakan \textit{package} \texttt{curl} secara bawaan.\\
        \textit{Cara Mengatasi}: Pada \textit{stage} \texttt{runner} di dalam berkas \texttt{frontend/Dockerfile}, ditambahkan instruksi instalasi \textit{package} \texttt{RUN apk add --no-cache curl} sebelum menyalin berkas konfigurasi Nginx. Setelah \textit{image} di-\textit{build} ulang, mekanisme \texttt{healthcheck} pada \textit{container frontend} berhasil berjalan normal dan mencapai status \texttt{healthy}.
  \item \textbf{Kompatibilitas Lockfile antara \texttt{pnpm} Lokal dan \texttt{npm ci} pada GitHub Actions}:\\
        \textit{Kendala}: Proyek \textit{frontend} diinisialisasi secara lokal menggunakan \textit{package manager} \texttt{pnpm} yang menghasilkan \textit{lockfile} \texttt{pnpm-lock.yaml}, sedangkan spesifikasi Soal 3 mewajibkan \textit{job} \texttt{frontend-build} pada GitHub Actions mengeksekusi \textit{command} \texttt{npm ci} yang mensyaratkan keberadaan berkas \texttt{package-lock.json}. Hal ini sempat menyebabkan status \textit{failed} pada eksekusi awal \textit{pipeline} CI.\\
        \textit{Cara Mengatasi}: Pada berkas \textit{workflow} \texttt{ci.yml}, ditambahkan \textit{step} pemeriksaan awal sebelum proses instalasi \textit{dependency} dijalankan. Apabila berkas \textit{lockfile} standar npm belum tersedia di dalam direktori \texttt{frontend}, \textit{runner} akan men-generate berkas tersebut terlebih dahulu menggunakan \textit{command} \texttt{npm install} dengan \textit{flag} khusus pembuatan \textit{lockfile}, sehingga \textit{step} \texttt{npm ci} dan \texttt{npm run build} berikutnya dapat dieksekusi hingga mencapai status \textit{passed}.
  \item \textbf{Konfigurasi Workflow Permissions dan Lowercase Image Name pada GHCR}:\\
        \textit{Kendala}: Ketika \textit{workflow} \texttt{deploy.yml} dikonfigurasi untuk menjalankan proses \textit{push image} menuju \texttt{ghcr.io}, pihak \textit{registry} menolak \textit{request} \texttt{docker push} apabila \texttt{GITHUB\_TOKEN} hanya memiliki akses \textit{read-only} atau apabila nama pemilik \textit{repository} seperti \texttt{FauzanTrisuladana} masih memuat karakter huruf kapital.\\
        \textit{Cara Mengatasi}: Pengaturan \textit{Workflow permissions} pada \textit{repository} GitHub diubah menjadi \textit{Read and write permissions}, ditambahkan deklarasi \texttt{permissions: packages: write} pada berkas \texttt{deploy.yml}, serta diterapkan normalisasi \textit{lowercase} menggunakan utilitas \texttt{tr '[:upper:]' '[:lower:]'} pada variabel pemilik \textit{repository} sebelum melakukan \textit{build} dan \textit{push image} ke GHCR.
\end{enumerate}

\section{Kesimpulan}

\par Berdasarkan seluruh tahapan perancangan arsitektur, implementasi kode, konfigurasi otomasi CI/CD, \textit{multi-stage containerization}, hingga orkestrasi \textit{multi-container} yang telah dilaksanakan pada Ujian Tengah Semester (UTS) ini, dapat ditarik kesimpulan sebagai berikut:
\begin{enumerate}[leftmargin=*]
  \item \textbf{Integrasi Arsitektur Full-Stack RESTful API Laravel 12 dan SPA Vue.js 3}:\\
        Sistem Informasi Akuntansi Pemuda berhasil diimplementasikan secara menyeluruh dengan memisahkan \textit{service backend} Laravel 12 dan \textit{frontend} Vue.js 3. Pengamanan seluruh \textit{endpoint} menggunakan \textit{Bearer token} Laravel Sanctum, standarisasi \textit{HTTP status code} (\texttt{200}, \texttt{201}, \texttt{401}, \texttt{422}), konfigurasi \textit{HTTP client} Axios berbasis \textit{environment variable} \texttt{VITE\_API\_URL}, serta pengujian otomatis melalui \textit{feature test} memastikan komunikasi data antara \textit{client} dan \textit{server} berlangsung secara aman dan konsisten.
  \item \textbf{Tata Kelola Repository Terproteksi dan Otomasi Quality Gate CI/CD}:\\
        Penerapan \textit{branch protection ruleset} pada \textit{branch} \texttt{main} dan \texttt{dev} berhasil mencegah \textit{direct push} dan menegakkan kewajiban verifikasi melalui \textit{Pull Request}. Pemisahan berkas \textit{workflow} menjadi \texttt{ci.yml} (untuk pengujian \texttt{php artisan test} dan \textit{build} \texttt{npm run build} di seluruh \textit{branch}) serta \texttt{deploy.yml} (khusus untuk \textit{event} \texttt{push} pada \textit{branch} \texttt{main}) menjamin bahwa hanya kode yang telah lulus \textit{quality gate} yang di-\textit{build} menjadi \textit{container image} dan di-\textit{push} ke GitHub Container Registry (\texttt{ghcr.io}) menggunakan \textit{tag} nomor \textit{commit} SHA.
  \item \textbf{Efisiensi Multi-Stage Build dan Performa Application Server FrankenPHP}:\\
        Penyusunan berkas \texttt{Dockerfile} pada sisi \textit{backend} yang menggunakan \textit{base image} versi spesifik FrankenPHP 1 PHP 8.4 Alpine serta pada sisi \textit{frontend} yang memadukan \textit{stage} \texttt{builder} Node.js 24 Alpine dengan \textit{stage} \texttt{runner} Nginx 1.27 Alpine berhasil mengoptimalkan pemanfaatan \textit{layer cache}, mengeliminasi direktori \texttt{node\_modules} dari \textit{final image}, dan menerapkan isolasi \textit{non-root user} (\texttt{www-data}). Rekaman \textit{runtime logs} dari \textit{container backend} membuktikan bahwa aplikasi dilayani secara langsung oleh FrankenPHP dan Caddy pada \textit{port} 80.
  \item \textbf{Keandalan Orkestrasi Podman Compose dan Kesiapan Live Deployment}:\\
        Orkestrasi melalui berkas \texttt{compose.yml} berhasil menjalankan \textit{service} MySQL, phpMyAdmin, \textit{backend} Laravel, dan \textit{frontend} Vue.js dalam satu \textit{bridge network} \texttt{kepl} dengan dukungan pemantauan \texttt{healthcheck} otomatis dan persistensi data pada \textit{named volume} \texttt{kepl\_mysql\_data}. Selain berjalan penuh pada lingkungan \textit{container} lokal, seluruh sistem juga telah berhasil di-\textit{deploy} dan dapat diakses secara publik melalui \textit{production environment} \url{https://kepl.trisuladana.com}.
